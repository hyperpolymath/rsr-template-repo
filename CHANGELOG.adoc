=== [Unreleased]

==== Fixed

* **The template's gates could not fail, and the toolchain was not minted.**
  Reported from JuliaPackageSpitter.jl and traced here; see
  `docs/reports/compliance/RSR-TEMPLATE-DAMAGE-2026-10-30.adoc` for the full
  investigation and the estate inventory.
** `spdx-headers` globbed `*.rs`/`*.res`/`*.gleam` and capped the scan at 20
   files, so it examined nothing and passed in every Julia, Idris2, Zig, Elixir,
   OCaml and shell repository. `scripts/check-spdx-headers.sh` derives the
   extension set from the languages the repository declares, scans every match,
   and fails when a declared language has no files or when it matched nothing;
** `container-images-pinned` asked whether `cgr.dev` appeared in the
   Containerfile, which `FROM cgr.dev/chainguard/wolfi-base:latest` satisfies.
   `scripts/check-container-pins.sh` requires a 64-hex digest on every `FROM`;
   `scripts/pin-container-digests.sh` writes the pins and refuses a placeholder;
** `mise.toml` was copied from the spine, not rendered, so every mint declared
   the template's own toolchain — nine runtimes including Python, which is
   banned estate-wide, and not the language of the repository. It is now
   rendered from the detected languages by `scripts/render-mise.sh`, and
   `scripts/check-mise-language.sh` fails a repository whose declared toolchain
   is not the one its languages need;
** `just quality` printed "All quality checks passed!" over verbs that reported
   `N/A` and exited 0. It now fails when a verb runs nothing, and the
   `julia-library` archetype wires `fmt`, `fmt-check` and `lint` to
   `scripts/julia-quality.jl`;
** `build/container/Containerfile` is deleted rather than pinned: two
   `FROM …:latest` lines and a body of TODO comments built nothing and failed
   `container-images-pinned` in every minted repository, including those that
   publish no image. A repository that publishes one adds the file and pins it
   (`scripts/pin-container-digests.sh`); `just container-build` says so;
** `archetypes/*/prune.txt` and `scripts/prune-archetype-modules.sh`: an
   archetype can remove spine modules its preset does not declare, so a Julia
   library no longer inherits a `Containerfile`;
** the mint's `.in` rename covered a hardcoded three-file list; it now covers
   the files the applied overlay actually added, so the spine's own `.in`
   templates survive;
** `check-no-placeholders.sh` died with exit 1 and no output in a repository
   with no `origin` remote (a fresh mint, before the first push): `git config`
   exited 1 and `set -e` took the script with it;
** `validate-template.sh` referenced an unset `SCRIPT_DIR` (aborting at Phase 6
   under `set -u`) and demanded `CONTRIBUTING.md` in an estate that writes
   `.adoc`. There is now a root `LICENSE` (MPL-2.0), so the Mustfile's
   `license-present` and every minted `link:LICENSE[LICENSE]` resolve;
** a pre-write token gate in `repo-init` refuses a mint the recipe cannot answer
   for, and four gates now run against the minted tree before handoff;
** `tests/workflows/mint_gates_test.sh` (30 controls) asserts that every gate
   fails on a fixture built to fail it; `tests/e2e/language_profiles_mint_test.sh`
   (27 controls) mints a Julia package and a Rust CLI and runs the gates on both.
   `.github/workflows/quality.yml` gained a `mint-gates` job that runs them.

* `repo-init` minting a repository created with GitHub's "Use this
  template" (measured on metadatastician/lintel, 2026-10-14):
** provenance recorded the CHILD's own HEAD as the template commit. The
   commit is now resolved by tree equality against the template's history
   (`scripts/resolve-template-pin.sh`), before anything is written, and an
   unresolvable tree aborts the mint (`RSR_TEMPLATE_URL`,
   `RSR_TEMPLATE_COMMIT`, `RSR_ALLOW_UNPINNED=1` for the exceptions);
** the template's name, owner and deed file are derived from the checkout
   (Justfile, then remote), not hardcoded, so a mint from a minted repo works
   (ported from lintel#9, which did not merge; its removal of the
   `[YOUR-REPO-NAME]` deed seds was not ported, since only they fill it);
** every rewrite pass and completeness check reads one file list: the
   repository's own files (`git ls-files`, plus untracked not-ignored), minus
   `.machine_readable/mint-verbatim.txt`. The strip pass no longer edits
   git-ignored sibling checkouts under `_build/`, nor the fixture tests its
   own leftover check exempts; `strip-instruction-blocks.rs` takes files, not
   a directory. `check-no-placeholders.sh` reads the same manifest;
** a fresh mint of main aborted on `julia_library_test.sh`'s package-UUID
   fixture token; it is now carried verbatim;
** the repository map is generated from the work tree (`gen-repo-map.sh
   --worktree`), after the last tree-changing step, so it no longer lists
   `archetypes/` and the template's deed name;
** stage 8 no longer tells a minted repo to arm `check-variant-drift.sh`,
   which a fresh mint cannot pass (101 rendered files differ); it points at
   `check-template-conformance.sh`. The (variant) clause now declares the
   mint's removals, and the drift gate says why it fails on a minted repo;
** deed-validate.yml's "Copy it from …" line names the template as the
   upstream source, so the self-name pass leaves it alone.
* `tests/e2e/use_template_mint_test.sh` (wired into estate-rules): the first
  CI job to run a full mint, with a negative control beside each check.
* The published governance badge could lie. `dogfood-gate.yml` mapped every
  non-`success` K9 outcome to RED, so `skipped`, `cancelled` and `timed_out`
  all rendered a red "failure" that never happened; worse, the `badges` job
  skipped publication entirely when its lane was skipped, so an earlier green
  badge stayed on display. Badge publication is now owned by
  `scripts/governance-badge.js`, which renders `success`/brightgreen,
  `failure`/red, and skipped/cancelled/unavailable/unrecognised as explicit
  lightgrey states, and which publishes on a skipped lane instead of leaving
  the old badge alone.
* Badge publication treated every GitHub API error as "the branch is missing":
  `gh api … >/dev/null 2>&1` fell through to branch creation on a 401, a 429 or
  a network failure, and a failed file read produced a PUT with no `sha` that
  could never converge. Only a 404 on both the file and the ref may now create
  a branch; auth, rate-limit, 5xx and network failures fail the run without
  writing anything.
* Every push to `main` wrote a badge commit even when the badge was unchanged.
  The publisher now fetches the published file, compares it byte for byte with
  the newly rendered badge, and exits with an "unchanged" notice and no commit
  when they are identical - and it never re-serialises the JSON to make the
  comparison succeed. Publications are serialised per repository (job-level
  `concurrency`), and the sha-checked contents call turns a race into a
  re-read instead of a silent overwrite.

* **The Hypatia verdict grid was described in three places and produced in
  none.** `.github/workflows/README.adoc` said a `verdict` job posted the grid,
  `.gitbot-fleet/report-backs/README.md` said the Hypatia lane downloaded the
  report-backs, and `fork-governance.yml` produced a `fleet-report-backs`
  artifact "for the grid" — while no workflow rendered a grid, and
  `hypatia-scan.yml` uploaded no findings file at all. `fork-governance.yml`'s
  verdict job now collects the producers' artifacts for one commit, renders the
  findings-family grid with the standards renderer (pinned commit, verified
  sha256, never a copy in this tree), uploads `verdict-grid` and maintains one
  `<!-- verdict-grid:hypatia … -->` comment per pull request. It is triggered by
  `pull_request` *and* by `workflow_run` on the two producer workflows, so it
  re-renders when a scanner finishes instead of showing "not yet" forever.
* **Hypatia ran twice per pull request.** `hypatia-scan.yml` and a
  `hypatia-scan` job of `static-analysis-gate.yml` each built the same scanner
  at the same pin, with separate caches and two independent "fail on critical"
  gates over two differently-shaped JSON files. Hypatia now runs once, in
  `hypatia-scan.yml`, which also uploads `hypatia-findings.relativized.json`
  (repo-relative paths, so the grid's delta column can match
  `git diff --name-only`) as `hypatia-scan-findings`. `static-analysis-gate.yml`
  keeps what is specific to it and uploads `static-analysis-findings`.
* **A failed fleet job was reported and then ignored.** The verdict job printed
  the fleet result in a table and never failed on it, so a fleet failure was
  invisible where a reader looked; its `jq '… | .findings | length'` loop could
  also abort the whole summary on one malformed envelope and skip the final
  check. The verdict now fails on DEED/K9 only (each producer owns its own
  gate), states that the fleet's failure is orange rows plus its own red check,
  and never parses fields it does not own.
* **`.hypatia-ignore` carried a dangling cross-reference**: `panicbot` was left
  unenrolled because "the Hypatia lane's direct panic-attack row" would cover
  it, and no such row existed. The grid now renders that row from
  `static-analysis-gate.yml` evidence, and the enrolment reason states the rule
  it is an instance of (one scanner, one row).

* **Seven defects the review of this work found, each now covered by a control.**
  None of these were reached by the tests as written, which is the point:
** `check-container-pins.sh` took the "nothing to pin" success path even after
   failing on a `Dockerfile`, so the one repository shape the Dockerfile rule
   exists to catch reported PASS; and it registered a stage name only after the
   line that `continue`s, so the ordinary `FROM image@sha256:… AS build` +
   `FROM build` pair was judged an unpinned remote image. Stage names are now
   registered when parsed, before any branch can skip the rest of the line;
** `pin-container-digests.sh` rewrote every `FROM` line, turning `FROM scratch`
   and `FROM build` into `scratch@sha256:…` and `build@sha256:…` — corrupting the
   multi-stage files it should leave alone, while the companion gate accepted the
   result. It now splits FROM into flags/reference/tail and rewrites only the
   reference of a remote image;
** `check-spdx-headers.sh` judged emptiness per EXTENSION, so a valid Elixir tree
   with `.ex` and no `.exs` (or OCaml `.ml` without `.mli`) failed for a language
   it is written in. Emptiness is now judged per language, across all of its
   extensions;
** `render-mise.sh --langs` only changed the label: the tool list still came from
   the tree's own detection, so a fixture asking for Julia was handed the docs
   toolchain. `mise-tools` now accepts the language list, and `--check` compares
   the declared toolchain rather than the rendered prose — which made it
   impossible to pass on any repository that wrote its own header, the template
   included;
** `check-mise-language.sh` parsed only bare `[tools]` keys, and backend-qualified
   tools MUST be quoted (`"npm:prettier"`), so the banned-tool check could never
   see them; its `--detect` mirror also looked only at the root, calling a tree
   with `src/interface/abi.ipkg` and `src/interface/ffi/build.zig` a docs
   repository. Both now follow the engine, depths included, and the mirror lists
   mise tools rather than each language's binaries;
** `check-mint-tokens.sh` treated "no build/just/repo-init.just" as proof of a
   minted tree — but that recipe is carried verbatim into every child, so no child
   was ever recognised and an unfilled `{{PROJECT_NAME}}` passed (and
   `survey-template-damage.sh` reported such repositories token-clean). The marker
   is `archetypes/`, which the mint deletes;
** `archetypes/*/prune.txt` dropped only `build/container/`, so a minted Julia
   package and a minted Rust CLI both carried the Idris2/Zig seam: three languages
   detected, `idris2` and `zig` installed, `idris2 --build` in `just build`. Both
   presets declare neither the abi nor the ffi capability, so both now prune
   `src/interface/`; `validate-rsr` requires the seam only of a tree that carries
   it. The archetype tests assert the toolchain is single-language.

==== Added

* `scripts/governance-badge.js` — the single implementation of the badge
  scheme: the state -> (message, colour) table, canonical rendering, the
  publication decision (create orphan branch / add file / update / no-op),
  API-error classification, and guards that refuse `main`, `master`, a
  repository default branch, or a path outside `badges/`. Runtime-agnostic
  (Bun or Node, `node:` builtins only), so it is unit testable.
* `tests/workflows/governance_badge_test.sh` and
  `tests/workflows/governance_badge_test.js` — hermetic tests wired into
  Estate Rules: the state table, byte-equal no-op, changed-bytes publication,
  orphan-branch creation with `parents: []`, grey states for missing/malformed
  lane evidence, malformed existing content, 404-vs-outage classification,
  conflict reconciliation and the source-branch guards, plus wiring checks run
  against a mutated workflow so they are proven able to fail. They supersede
  `tests/workflows/dogfood_badge_test.sh`, which asserted the old mapping and
  was never wired into CI. A present but *unreadable* artifact (EACCES, or a
  TOCTOU deletion between the stat and the read) is now evidence that cannot be
  checked rather than an uncaught exception: it renders grey, names the errno,
  and exits 3. The assertion is skipped, with the reason printed, when the
  suite runs as root, where `chmod 000` cannot deny a read.
* `README.adoc` and `.github/workflows/README.adoc` now state the operational
  contract of the generated `governance-badges` branch: it is an orphan with no
  common ancestor with `main`, it is never merged and has no pull request,
  recent pushes are normal refreshes, identical content makes no commit, and a
  grey badge means the lane produced no trustworthy result.

* `www/` site-operations bundle (issue #53): canonical `.well-known/`
  metadata, publishable content, policy sources, error bodies,
  security-header templates, Caddy/nginx/Apache integration examples, an
  authoritative-only BIND 9 starting hand with record templates,
  encrypted-DNS/privacy and TLS guidance, explicit opt-in profiles,
  schemas, planted-control tests and operational runbooks.
* `scripts/migrate-wellknown-to-www.sh` — conflict-safe migration of a
  repository-root `.well-known/` into `www/.well-known/` (identical copies
  de-duplicated, root-only content moved, divergent content quarantined —
  see Changed).
* `scripts/sweep-wellknown.sh` — stage 5 (#119) batch driver: classify,
  migrate, test and commit across the estate in batches of 25, holding
  Pages-served and non-RSR repositories for a human decision instead of
  sweeping them blind.
* `www/runbooks/stage5-wellknown-sweep.adoc` — how to run the sweep, and
  how to recover from a quarantine.
* Mint wiring for the `www/` bundle: `repo-init` now invokes
  `scripts/migrate-wellknown-to-www.sh` when the tree being minted still
  carries a legacy root `.well-known/`, and runs `www/tests/run-all.sh`
  afterwards. Both are no-ops for a repository minted from the current
  template; they exist for running `repo-init` over a tree that predates
  #53. #106 described both as already present — neither was, which is a
  fair part of why the estate still carries root `.well-known/` directories.
* `scripts/merge-actions-lock.rs` — merges an archetype's lock fragment
  (`archetypes/<name>/actions.lock`) into the spine's
  `.github/workflows/actions.lock` at mint. A record that differs between
  the two stops the mint. `tests/workflows/archetype_lock_merge_test.sh`
  (wired into estate-rules) checks the merged lock with
  `check-lock-sync.sh`, and checks that the old clobber, a missing record
  and a conflicting record all fail.

* `scripts/verdict-grid-lane.sh` — collect / validate / render / previous /
  comment for the verdict grid lane. It refuses to execute a renderer whose
  sha256 does not match the recorded digest, renders an explicit **orange
  "indeterminate"** grid (never green) when the renderer or the evidence is
  unavailable, refuses a bare panic/pons findings array (a bare array cannot
  distinguish "ran clean" from "never ran"), and updates the comment it posted
  last time instead of adding one per run.
* `scripts/check-workflow-edges.sh` — the intra-repository half of the CICD
  Squabbler gate, run in both `squabble.yml` and `estate-rules.yml`. It fails
  when a `workflow_run.workflows` entry names no workflow's `name:`, when two
  workflows share a `name:`, when the verdict job reads an artifact its named
  producer never uploads, when a producer stops running on `pull_request`, when
  the verdict job's `--hypatia-ref`/`--panic-ref`/`--pons-ref` disagree with the
  producer's pin, or when one tool is pinned at two different commits.
* `scripts/check-hypatia-ignore.sh` — the meta-rules for `.hypatia-ignore`:
  every fragment must end on a path boundary (a substring fragment silences
  more than it names), no entry may be subsumed by a broader one for the same
  module, the path it names must exist, and it must belong to a commented
  reason block.
* `docs/HYPATIA-RULE-ORDER.adoc` — the ordered statement of Hypatia's exemption
  layers (total ban, universal excludes, built-in defaults, `.hypatia-ignore`,
  inline directives, baseline, grid normalisation), the eight clashes found
  between them, the rule that resolves each, the e/r (evidence/reason)
  contract per reporter, the GitBot design rules, what is deliberately *not*
  enforced, and the refusals that make the order a checked contract.
* `tests/workflows/verdict_grid_test.sh` (70 checks), `workflow_edges_test.sh`
  (21) and `hypatia_ignore_test.sh` (22) — behaviour, wiring and firing controls
  for the three scripts above, with stub `gh`/renderer and mutated workflow
  copies, so every check is proven able to fail.
* `.machine_readable/policies/hypatia-rule-order.json` — the rule order as a
  contract rather than prose: the seven layers with their rank, scope, owner and
  what each may override; the eight concerns with exactly one owning workflow or
  file each; the eight clashes with the rule that resolves each; the modules
  `.hypatia-ignore` currently exempts and the layer each exemption lives in; and
  the scanner, grid, renderer and jq-library pins the order was written against.
* `scripts/check-hypatia-rule-order.sh` — refuses a duplicate or gapped rank, a
  layer that states no scope or no override, an owner outside the four declared
  parties, a concern owned by a path that does not exist, a clash with no
  resolution, a module exempted but unclassified (or classified but no longer
  exempted), an exemption filed under a layer this repository may not change,
  and any pin or digest that disagrees with `hypatia-scan.yml` or the lane
  script. Exit 0 clean, 1 violation, 2 setup error.
* `tests/workflows/hypatia_rule_order_test.sh` (44 checks) — one mutation per
  refusal above, run against a copy of the real policy. Two of its own first-draft
  defects are documented in `docs/HYPATIA-RULE-ORDER.adoc`: `@tsv` collapses an
  empty field (a missing `overrides` was reported as a missing `scope`), and
  `grep` under `set -e` exits before a missing pin can be diagnosed.
* `.machine_readable/policies/README.adoc` — the registry now says what each
  policy states, what checks it, and that adding a policy means adding the
  checker and its lane.
* `scripts/run-proven-suite.sh` gains the lane *Hypatia rule order & clash
  resolution*, so the policy cannot drift from the four files it describes
  without a red run; `tests/run_proven_suite_test.sh` asserts the lane is
  dispatched (16).

==== Changed

* KYAML, step 5 of standards YAML-POLICY §5 (standards#1024): the three
  estate-owned YAML files that no third-party bot rewrites are now KYAML
  content: `build/container/compose.yaml`, `compose.example.yaml` and
  `stapeln/.gatekeeper.yaml`. Each keeps its name, because Compose, the
  Containerfile label and svalinn find it by name (§3.4). They were rewritten
  by standards' `kyaml-format.sh` alone, which refuses any change to the
  parsed data. Every comment line survives, and `.gatekeeper.yaml` is now
  byte-identical to standards' `_shared/container/.gatekeeper.yaml`.
  Estate Rules gains the ratchet "Converted YAML stays KYAML", which runs
  that script at standards `75bd599` with yq 4.53.3, both sha256-verified.
  Container narrowing at mint can delete any of the three files, so the
  template must keep all of them, while a minted repository checks the ones
  it kept and names the ones narrowing removed.
  `tests/workflows/kyaml_ratchet_test.sh` covers the template and each
  narrowing, and `tests/workflows/container_kyaml_test.sh` checks that the
  conversion kept every value in the template's configs. Estate Rules runs
  both.
  Workflows wait for step 6 (standards#1025). Files that Dependabot,
  FUNDING, issue forms, Probot settings, CodeRabbit, Copilot, GitLab CI or
  pre-commit read or rewrite are not converted, as in standards.
* The workflow linter installs Bun 1.4.2, the estate pin, from its release
  archive and checks its sha256, as Estate Rules installs its tools. It ran
  `oven-sh/setup-bun@v2.2.0` with `bun-version: latest`, so the runtime was
  unpinned, and SonarCloud rated a third-party action pinned by tag "C"
  ("Use full commit SHA hash"), even though `actions.lock` pins its commit.
  The linter's lock edge to setup-bun goes. The `setup-bun@v2.2.0` record
  stays, because the commented Bun steps in `e2e.yml.template` resolve
  through it.
* `.github/workflows/runtime-policy.yml` is removed, folded into governance
  as the standards cicd-regularisation spec §14 rules. Governance's
  "Language / package anti-pattern policy" fails any tracked
  `package-lock.json`, a stricter test than this file's mixed-toolchain error,
  and its "JS runtimes" jobs check `bun.lock`, `deno.lock` and
  `pnpm-lock.yaml` against `package.json`. Its `actions.lock` record goes with
  it, and `validate-template.sh` and `validate_workflows_test.sh` require
  `governance.yml` in its place. Repositories minted from the template stop
  receiving their own copy of the check. Governance now runs on pull requests
  to any branch, as the removed workflow did, so a stacked pull request keeps
  the check. `tests/workflows/runtime_policy_fold_test.sh`, which Estate Rules
  runs, checks that both validators reject a tree without `governance.yml` and
  accept none of the retired gates' names in its place.
  `tests/workflows/governance_policy_test.sh`, also in Estate Rules under a
  sha256-verified Bun 1.4.2, checks that the workflow and its lock record stay
  gone, that governance's pull request trigger has no filter, and that its
  standards call matches the lock.
* JavaScript runtimes follow the 2026-10-14 ruling (standards
  LANGUAGE-POLICY §1.3–§1.4): Bun > Deno > pnpm > npm, from one
  `package.json` whose `bun.lock`, `deno.lock` and `pnpm-lock.yaml` are all
  written by `js-runtimes regen`.
** `.github/workflows/runtime-policy.yml` used to fail any repository
   carrying more than one lock, so it failed every repository that follows the
   ruling ("Mixed toolchains: 3 package managers"). Those three locks now count
   as one dependency graph. `package-lock.json` next to them still fails. A
   `deno.json` is a notice, not a warning.
** The provisioning engine (`build/just/provision-lib.sh`,
   `provision-modes.sh`, `provision-check.sh`) is re-synced to standards
   `ed04132e` (engine 0.6.0, standards#1255). A `package.json` provisions bun,

** The same policy appears in the arrival pack (`arrival-pack.ncl`, and
   CLAUDE.md regenerated from it), `mise.toml`, `docs/SETUP.adoc` PV-W23,
   PV-W30 and PV-W34, the dev warm-up, `.cursorrules`, `.clinerules`,
   `.windsurfrules`, `.github/copilot-instructions.md` and the PR template.
** The six standards reusables move from `ae36881` to `934b879`. At
   `ae36881` governance's Actions lockfile verify installs gh-actions-lock
   v0.1.6, which cannot read this lock's format v0.0.3 (exit 2, red on main).
   `actions.lock` is re-keyed and closed at the new pin (setup-bun and

* Canonical `.well-known/` location moved from the repository root to

==== Changed

* Divergent root/`www/` `.well-known/` content is now quarantined to
  `www/.legacy-well-known-<YYYYMMDD>/` instead of being left in place: the
  estate-wide sweep (#119) is unattended, so a conflict must not halt it, and
  must not be silent either. The `www/` copy is untouched, both hashes are
  printed, and the run exits non-zero. `--in-place` keeps the previous
  contract (preserve both, exit 1) for hand resolution. The quarantine lives
  under `www/` rather than at the root because the root allowlist is matched
  literally and bidirectionally, so a dated root directory would report as
  drift in every repository swept.

==== Fixed

* Governance, Hypatia Security Scan, Mirror to Git Forges, Rust CI and
  Secret Scanner start again. GitHub's runner now rejects a lock record whose
  `ref:` is the record's own SHA ("invalid lockfile pin"), and nine of this
  lock's action records had one. The standards reusables move from `6a92510`
  to `75bd599`, whose own lock carries tag refs
  (hyperpolymath/standards#1271, hyperpolymath/standards#1285), and
  `relock-standards-pin.sh` at `75bd599` gave the nine records the same tags.
  No commit changes: each tag was checked to point at its recorded commit.
* The mint's self-name pass keeps issue references. It rewrote
  `rsr-template-repo#N`, a reference to this template's own issue, into
  `<child>#N`, which names an issue of the child that does not exist or is
  unrelated. resource-algebra carried such references after its mint.
  `tests/workflows/self_name_pass_test.sh` (wired into Estate Rules) runs
  the recipe's own rewrite program on fixtures.
* CLAUDE.md prints the deed's typed identity (`#u5"<name>"`) instead of
  the derived uuid5 in hex, and the deed's identity comment no longer
  spells it out. ADR-008's strict v8 gate (governance "UUID v7
  conformance") rejected both, in the template and in every minted repo.
* The standards reusables are pinned to `6a92510`, whose governance job
  installs gh-actions-lock v0.2.0. At `ae36881` it installed v0.1.6, which
  refuses lock format v0.0.3 ("newer than this binary supports"), so
  Actions lockfile verify failed. `actions.lock` was relocked with
  standards' `propagate-workflow-pins.sh` (hyperpolymath/standards#1254).
  `6a92510` also scans the julia-library overlay's `Project.toml.in` as a
  `Project.toml` (hyperpolymath/standards#1258), so its `[extras]` registry
  UUIDs no longer fail the strict v8 gate.
* The non-interactive mint completes. `RSR_NON_INTERACTIVE=1` used to
  stub `read` for the whole recipe, so an unanswered prompt killed the
  mint under `set -u` and the substitution loops never ended. Prompts now
  read answers from the environment; `tests/workflows/non_interactive_mint_test.sh`
  drives that path in Estate Rules, and the docs that warned agents off it
  now describe it.
* A mint leaves just's own interpolation of `project` alone, regenerates
  CLAUDE.md and the repository map from the child's deed and tree, keeps
  the deed's `reject-if-contains` detector, and no longer breaks the
  OpenSSF audit table when no OpenSSF id is given.
* The standards reusables are pinned to standards main (`ae36881`), where
  the Actions lockfile verify job pins its tool and treats `sha-as-ref`
  as advisory.
* The julia-library lock fragment is at the spine's lockfile format
  v0.0.3, so Julia mints merge it again.

* Julia mints start with Lock Sync green. The julia-library overlay
  shipped its own `actions.lock`, which replaced the spine's at mint, so
  every spine workflow lost its records. The records now ship beside the
  overlay and are merged in. The overlay workflows gain SPDX headers and
  top-level permissions, and julia-docs builds with plain steps instead of
  the allowlist-refused julia-buildpkg/julia-docdeploy. julia-actions/cache
  moves to v3.5.0. The root allowlist admits `?Project.toml` and `?test/`.
  The docs checkout sets `persist-credentials: false`, so package code run
  while the docs environment is set up finds no stored token. deploydocs
  still receives GITHUB_TOKEN.
* `just repo-init julia-library` accepts a `<Name>.jl` slug. The PROJECT
  tokens map its dot to an underscore, and the default service name is the
  slug in lower case.

* Dev container starts for everyone: dropped the ghcr.io dev container
  features (anonymous pulls returned 403), installing just from Wolfi and a
  SHA-256-checked Nickel 1.17.0 binary instead. The default
  `.devcontainer/devcontainer.json` now targets rootless Podman
  (`--userns=keep-id:uid=65532,gid=65532`, `label=disable`) so the workspace
  is writable as wolfi-base's built-in `nonroot`; Docker, Codespaces and
  Gitpod use `.devcontainer/docker/devcontainer.json`.
* `dot-wellknown-enforcement.yml` now drives the migrator that #106 described
  but never wired up: previously the workflow only printed advice to run it,
  so nothing verified that a repository would survive the migration. It now
  runs the migrator in `--dry-run` and turns every conflict into a
  `::warning` annotation — a warning, not an error, for the migration window.
* The migrator's acceptance test had encoded the in-place contract as the
  required behaviour, contradicting #106's stated design; it now proves the
  quarantine contract across nine scenarios, including the collision case
  where a quarantine name is already taken.
* `tests/e2e/template_instantiation_test.sh` fed the three container answers
  only when `container/` existed, but `build/just/repo-init.just` asks those
  questions when `build/container/` does. On any complete checkout — which is
  what CI clones — the recipe asked three questions the test had no answers
  for, `read` hit EOF, and the recipe exited 1, so the instantiation e2e was
  red at the container prompt. The guard now matches the recipe's own path.
  (The test also needed `ruby` for the two mint tools. Those are Rust as
    of 2026-09-18, so it no longer stops there.)
